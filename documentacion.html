AgroSense

Sistema de Agricultura Inteligente con Arquitectura de Microservicios

Autor / Alumno: Fabricio Montoya

Materia: Programación / Arquitectura de Software

Plataforma: Spring Boot 3.4 • Java 25 (LTS) • PostgreSQL • JUnit 5 • Jakarta Validation (DTOs)

Repositorio GitHub: https://github.com/montoyafabricio/agrosense

Fecha: Noviembre 2026

1. Introducción y Objetivos

AgroSense es una solución backend orientada a microservicios diseñada para la digitalización y monitoreo telemétrico de parcelas agrícolas.

  • Administrar de forma centralizada a los productores agrícolas y sus respectivos cultivos.
  • Gestionar la instalación de sensores ambientales (humedad y temperatura).
  • Registrar lecturas periódicas históricas (mediciones).
  • Evaluar de forma automática reglas agronómicas para generar alertas tempranas (estrés hídrico, exceso de humedad o temperaturas críticas), permitiendo optimizar el riego y prevenir daños en los cultivos.

3. Arquitectura de Software (Microservicios + Gateway)

Para garantizar alta cohesión y bajo acoplamiento, la solución se estructuró en 4 microservicios de dominio y 1 API Gateway:

[ Clientes / Postman / Frontend ] │ HTTP Puerto 8080 ▼ ┌───────────────────────────────┐ │ API GATEWAY │ │ (Puerto 8080) │ └───────────────┬───────────────┘ │ ┌──────────────────┬──────────┴───────────┬──────────────────┐ │ :3001 │ :3002 │ :3003 │ :3004 ▼ ▼ ▼ ▼ ┌─────────────────┐ ┌─────────────────┐ ┌───────────────────┐ ┌─────────────────┐ │ GestionService │ │ SensorService │ │ MedicionService │ │ AlertaService │ │ (Productores │ │ (Sensores) │ │ (Mediciones y │ │ (Alertas) │ │ y Cultivos) │ │ │ │ Reglas) │ │ │ └─────────────────┘ └─────────────────┘ └───────────────────┘ └─────────────────┘ │ │ │ │ Esquema gestion Esquema sensores Esquema mediciones Esquema alertas └───────────────────┴─────────────┬───────┴───────────────────┘ ▼ PostgreSQL (Base: agrosense)
  • API Gateway (Puerto 8080): Único punto de acceso público. Enruta hacia los microservicios preservando métodos, headers, query params y body. Si un microservicio no responde, devuelve HTTP 503. Expone GET /health.
  • GestionService (Puerto 3001): Administra Productores y Cultivos. Protege contra borrados indebidos de productores con cultivos o cultivos con sensores/alertas.
  • SensorService (Puerto 3002): Gestiona el parque de sensores y valida por HTTP la existencia del cultivo en GestionService.
  • MedicionService (Puerto 3003): Recibe lecturas, comprueba que el sensor esté activo, evalúa las reglas climáticas y despacha alertas. Habilita reintentos mediante POST /api/mediciones/:id/procesar.
  • AlertaService (Puerto 3004): Persiste alertas y gestiona la idempotencia para evitar duplicados en reintentos.

4. Base de Datos y Persistencia (PostgreSQL)

Se utilizó PostgreSQL mediante una única base de datos denominada agrosense, dividida en cuatro esquemas lógicos independientes:

  • gestion: tablas productores y cultivos.
  • sensores: tabla sensores.
  • mediciones: tablas mediciones y mediciones_procesamiento.
  • alertas: tabla alertas.

Decisión de Arquitectura: Respetando las directrices de diseño modular y microservicios, no existen claves foráneas (FOREIGN KEY) entre tablas de esquemas pertenecientes a dominios distintos. La integridad referencial entre módulos se valida estrictamente a nivel de servicio en Spring Boot mediante validaciones programáticas e inyección de dependencias.

5. DTOs y Validaciones (Zod)

Cada microservicio desacopla las solicitudes entrantes y salientes mediante Data Transfer Objects (DTO) con la librería Zod:

  • Modo Estricto (.strict()): Rechaza cualquier campo que no pertenezca a la entidad.
  • Inmutabilidad de identificadores: El cliente no puede suministrar su propio id al crear recursos; siempre es asignado por el servidor como UUID v4.
  • Actualizaciones completas (PUT): Se exige la totalidad de los atributos editables para garantizar la consistencia del recurso (sin soporte de PATCH parcial).
  • Validación estricta de rangos: Temperaturas finitas, humedad acotada entre 0 y 100%, y fechas válidas en calendario.

6. Reglas Automáticas de Agricultura Inteligente

El servicio MedicionService centraliza la evaluación climática con comparaciones estrictas:

Regla Condición Estricta Tipo Alerta Prioridad Mensaje Preventivo
1. Humedad Baja humedad < 30.0% RIEGO Alta Revisar la necesidad de riego por déficit hídrico.
2. Humedad Alta humedad > 80.0% EXCESO_HUMEDAD Media Revisar el drenaje antes de regar para evitar anegamiento.
3. Temperatura Alta temperatura > 35.0°C CALOR Alta Revisar las condiciones del cultivo por estrés térmico.

Los valores de corte exactos (30.0, 80.0 y 35.0) no disparan alertas. Una misma medición puede generar múltiples alertas simultáneas (por ejemplo, temperatura 38°C y humedad 20% disparan conjuntamente RIEGO y CALOR).

Manejo de Idempotencia: Como la entidad Alerta no tiene medicionId en el diagrama original, la prevención de alertas duplicadas se implementó técnicamente en AlertaService mediante verificación temporal y de tipo, permitiendo reintentar mediciones pendientes sin duplicar registros.

8. Limitaciones Técnicas del Prototipo

  1. Requerimiento conjunto de variables: Por especificación del prototipo académico, toda medición exige registrar temperatura y humedad simultáneamente, aun cuando el sensor físico haya sido catalogado como univariable.
  2. Consistencia eventual frente a transacciones distribuidas: No se implementa un coordinador pesado de 2PC (Two-Phase Commit). La consistencia ante fallos se resuelve por compensación lógica: la medición se guarda con estado pendiente y se provee el endpoint de reintento idempotente.
  3. Carácter informativo de las alertas: El software emite notificaciones orientativas y no acciona directamente bombas ni electroválvulas en campo.

9. Conclusiones

El proyecto AgroSense demuestra el diseño e implementación exitosa de un ecosistema backend moderno, desacoplado y resiliente, desarrollado en Java 25 (LTS) bajo Spring Boot 3. La separación en cuatro esquemas dedicados en PostgreSQL, el diseño basado en DTOs con Jakarta Validation, el motor de reglas agronómicas y la cobertura integral con JUnit 5 garantizan un sistema escalable, fuertemente tipado, seguro y fiel al modelo conceptual de clases planteado.
